### Bugs found
- `app/api/programmes/[id]/save-tree/route.ts:60,77-94` — Suite B — payload with two `weeks[]` entries sharing the same `id` — both pass the ownership check, then the sequential delete+insert loop processes them in order and the second occurrence's delete wipes the first occurrence's just-inserted sessions. Returns `200 {ok:true}` while silently discarding data. Last night's (2026-07-07) "save-tree data loss" fix validates weeks exist/are owned but does not dedupe week ids — this is a residual edge of the same bug class.
- `app/api/programmes/[id]/save-tree/route.ts:60` — Suite C — weeks whose `id` fails `isValidUuid` or isn't in the caller's owned set are silently filtered out of `targetWeeks` with no error surfaced; client gets `{ok:true}` believing the full tree saved when part of it was silently dropped (stale cache, concurrent edit, or malformed id all trigger this).
- `app/api/programmes/[id]/save-tree/route.ts:70` — Suite C — `day_of_week` range check (`>=1 && <=7`) has no `typeof === 'number'` guard, so a numeric string (`"3"`) or float (`3.5`) passes via JS coercion and reaches the DB unvalidated.
- `app/api/clients/route.ts:105-106` — Suite B — `start_date`/`renewal_date` have zero format/range validation before insert (unlike `program_length_weeks`/`manual_price_numeric`, which are validated) — malformed input raw-500s from Postgres, or nonsense dates (`1900-01-01`, `9999-12-31`) are silently stored.
- `app/api/agreements/[id]/route.ts:122-127` — Suite B — `goal_target_date` validated only via `isNaN(new Date(val).getTime())`, which accepts calendar-invalid dates that JS silently rolls over (e.g. `2026-02-30` → March 2) and far-past/far-future values with no bounds check.
- `app/api/portal/photos/route.ts:36-38` — Suite B — `taken_at` regex `^\d{4}-\d{2}-\d{2}$` checks shape only, not calendar validity — `2026-13-99` passes the app-level check and would raw-500 out of Postgres instead of a clean 400.
- `app/api/clients/route.ts:33-35` — Suite C — `full_name` validation is gated behind `typeof full_name === 'string'`, so a non-string (number/object/array) skips validation entirely and reaches `profiles.upsert(...)` unvalidated; additionally this field skips `stripHtmlTags` (used elsewhere in the codebase for name/title/notes fields), relying solely on React auto-escaping downstream — inconsistent with the defense-in-depth pattern used on comparable fields.
- `app/api/clients/route.ts:120-149` — general — if the Stripe setup call throws, the error is only `console.error`'d and swallowed; the response still returns `201` with `stripe_client_secret: null`, so the client record is created (quota consumed) but the caller has no signal that billing setup failed.
- `app/api/admin/pts/[ptId]/route.ts:24` — Suite B — `free_client_quota` validation (`typeof !== 'number' || x < 0`) admits `NaN`, `Infinity`, and non-integers (e.g. `3.7`) — no `Number.isFinite`/`Number.isInteger` guard, no upper bound.
- `app/api/templates/route.ts:100` — Suite C — `items.map(item => ({...item, template_id}))` spreads raw request-body objects directly into the `session_template_items` insert with no per-field validation (`exercise_id` UUID shape, `sort_order` numeric type, `prescribed_metrics` shape) and no allowlist of keys — relies entirely on DB constraints (only the FK case is explicitly handled) to reject bad data.
- `app/api/templates/[id]/duplicate/route.ts:47` — Suite B — `` `Copy of ${source.title}` `` is inserted with no length clamp, unlike `programmes/[id]/duplicate/route.ts:48` which truncates to 100 chars — duplicating a near-max-length title risks an unhandled raw DB error if `session_templates.title` has a length constraint.
- `app/api/clients/[id]/resend-invite/route.ts` — general — no rate limiting on invite resends (confirmed no rate-limiting utility exists anywhere in `lib/`); an authenticated PT can spam a client's inbox by repeated calls.
- `app/api/clients/route.ts:120` — general — `manual_price_numeric` is gated with a truthy check (`if (manual_price_numeric && ...)`), so a legitimately-validated `0` (free plan, allowed since the validation only rejects `< 0`) is treated as "no price" and silently skips Stripe setup — inconsistency between validation and business logic, may be intentional but undocumented.

**Lower-severity / informational (not logged as standalone bugs, noting for awareness):** `admin/set-role` blocks admin self-demotion to `'client'` but not to `'pt'` (admin-only endpoint, low exploitability); `bug-reports` admin check (`user.email !== adminEmail`) doesn't pre-check `adminEmail` is set, unlike the other three admin routes (not currently exploitable); `pt/avatar`/`pt/logo` cast `formData.get()` `as File` without `instanceof` check but fail safe if given a non-file; `programmes/[id]/route.ts` PATCH doesn't guard against a JSON-array request body before using `in`, low practical impact; `exercises/video` MIME allowlist trusts client-supplied `file.type` rather than sniffing magic bytes; no standalone "create single session" or "edit session in place" (PATCH/PUT on `sessions/[id]`) endpoint was found in scope — worth confirming with the team whether that's intentional.

### Bugs fixed
- **refs 71/72/73 (`save-tree` hardening)** — `POST /api/programmes/[id]/save-tree` had three related gaps in the same validation block: (1) a payload with two `weeks[]` entries sharing the same `id` both passed the ownership check, then the sequential delete+insert loop let the second occurrence's delete wipe the first occurrence's just-inserted sessions — silent data loss behind `200 {ok:true}`; (2) weeks whose `id` failed `isValidUuid` or weren't in the caller's owned set were silently filtered out of `targetWeeks` with no error surfaced, so the client believed the full tree saved when part was dropped; (3) the `day_of_week` range check had no `typeof === 'number'` guard, so `"3"` (string) or `3.5` (float) passed via JS coercion. Fix: reject duplicate week ids up front (400, no writes); reject the whole request (400) if any week doesn't resolve to an owned week; added `typeof === 'number' && Number.isInteger()` to the day-of-week guard. `app/api/programmes/[id]/save-tree/route.ts`. Verified live: duplicate id → 400, unowned id → 400, `day_of_week: "3"` → 400, `day_of_week: 3.5` → 400, and a valid payload targeting two distinct weeks still saves both weeks' sessions correctly with no cross-wipe (positive regression check).
- **refs 74/75/76 (shared calendar-date validation)** — three routes accepted dates with either no calendar-validity check or a shape-only regex: `POST /api/clients` (`start_date`/`renewal_date`) had zero validation (`1900-01-01`/`9999-12-31` silently stored); `PATCH /api/agreements/[id]` (`goal_target_date`) used `isNaN(new Date(val).getTime())`, which silently rolls invalid dates over (`2026-02-30` → March 2) instead of rejecting them; `POST /api/portal/photos` (`taken_at`) used a shape-only regex (`^\d{4}-\d{2}-\d{2}$`) that let `2026-13-99` through to a raw Postgres 500. Fix: added a shared `isValidDateString()` helper to `lib/utils.ts` (shape check + `date-fns` `parseISO`/`isValid` for real calendar validity + a 2000–2100 year sanity bound), applied at all three call sites. `lib/utils.ts`, `app/api/clients/route.ts`, `app/api/agreements/[id]/route.ts`, `app/api/portal/photos/route.ts`. Verified live: `2026-02-30`/`2026-13-99`/`9999-12-31` all now 400; a `goal_target_date: null` clear still succeeds (200, no regression).
- **ref 77 (`clients.full_name` typeof-gate bypass)** — validation was gated behind `typeof full_name === 'string'`, so a non-string (number/object/array) skipped validation entirely and reached `profiles.upsert(...)` unvalidated; it also skipped `stripHtmlTags`, unlike comparable name/title fields elsewhere in the codebase. Fix: reject non-string `full_name` with 400, apply `stripHtmlTags` before use. `app/api/clients/route.ts`. Verified live: `full_name: 12345` → 400.
