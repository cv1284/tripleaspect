### Bugs found
- **BUG-59** — `POST /api/portal/photos`, Suite A (happy path, valid `image/jpeg` ≤10MB) — 500 `"Bucket not found"`. The `progress-photos` Supabase Storage bucket referenced by `supabase/migrations/007_progress_photos.sql` does not exist in this project, so progress-photo upload is completely broken end-to-end (not just a test-data issue — the DB insert is never reached).
- **BUG-60** — `POST /api/exercises` (and identically `PATCH /api/exercises/[id]`), Suite C, `default_video_url: "javascript:alert(1)"` — accepted and stored verbatim (only a length cap is enforced, no scheme allowlist). Renders straight into `<img>`/`<video src>` in `components/client/VideoPlayer.tsx` with no sanitization. Modern browsers block `javascript:` in `img`/`video` `src` so not directly exploitable today, but there's no allowlist at all, unlike the equivalent field on agreements (`parq_storage_url` etc., which already do this correctly).
- **BUG-61** — Session creation (`sessions`/`session_items` tables), reached only via a **client-side-only** Supabase insert in `components/pt/SessionBuilder.tsx` — there is no Next.js API route for it at all. Confirmed via direct Supabase REST calls (PT's own JWT + anon key, bypassing the app's JS entirely) that `title`/`notes` accept unsanitized `<script>` tags and SQL-injection-shaped strings verbatim, and a 50,000-character title is accepted with no length cap. React's default escaping means this isn't live-exploitable as XSS today, but it's an architecture gap relative to every other content-creation entity in the app (all of which validate server-side).
- **BUG-62 (critical, IDOR)** — `POST /api/programmes/[id]/save-tree` checks that the *programme* in the URL belongs to the caller, but never checks that `week.id` values inside the request body belong to that programme. Reproduced safely (same-PT, two own programmes) by seeding Programme B's week with a session, then calling save-tree on **Programme A's** URL while referencing **Programme B's** week id — Programme B's week was silently wiped and overwritten. Since week UUIDs are visible in `GET /api/programmes/[id]` responses (including for `is_public` programmes any PT can fetch), this is very likely exploitable cross-tenant: any PT could destroy/overwrite another PT's programme content.
- **BUG-63** — `GET /api/inactivity-response` (public, email-link, token-authenticated) — a malformed token whose signature segment doesn't decode to exactly 32 bytes crashes `lib/inactivity-token.ts`'s `verifyToken()` with an uncaught `RangeError` from `timingSafeEqual`, producing a raw HTTP 500 instead of the friendly "link expired" page. This endpoint receives arbitrary/malformed input from email-link scanners and proxies in the wild.

### Bugs fixed

**BUG-62 (CRITICAL) — IDOR in `POST /api/programmes/[id]/save-tree`.** The route checked that the *programme* in the URL belongs to the caller but never checked that `week.id` values in the body belong to that programme — any of the PT's own other programmes' weeks (and, per Phase 1b's analysis, potentially another PT's if RLS were ever misconfigured) could be silently wiped via a different programme's URL. Fix: query `programme_weeks` scoped to `programme_id = [url id]` and filter the request body against that owned set before writing (`app/api/programmes/[id]/save-tree/route.ts`). Verified live by reproducing Phase 1b's exact attack (Programme A's URL referencing Programme B's week id) — now returns `{ok:true}` but Programme B's sessions stay untouched (confirmed `[]` before and after).

**BUG-59 (HIGH) — Progress photo upload completely broken in production.** Turned out deeper than Phase 1b's own diagnosis: fixing the reported "Bucket not found" 500 by creating the `progress-photos` Storage bucket (via the Storage Admin REST API, using `SUPABASE_SERVICE_ROLE_KEY`) surfaced a second failure — the `progress_photos` table from migration 007 had never been applied to the live DB either. This feature has been marked "shipped" in the Notion roadmap since 03 Jun 2026 but was dead on arrival. Discovered mid-fix that the Supabase CLI (`npx supabase`) is installed and already linked to this project (`brigid-pro` / `emxnmfmjxlhdrjibvmya`) even though `supabase migration list` shows empty remote history for every migration 001–015 (history tracking just isn't used here — DDL has always been applied out-of-band). Used `supabase db query --linked --file` to apply `007_progress_photos.sql` and a new `015_progress_photos_bucket.sql` (bucket + storage.objects RLS policies, mirrors the existing `pt-logos` bucket pattern). Verified end-to-end live: client photo upload → 201 → delete → 200, no orphaned storage objects, `GET /api/portal/records` unaffected.

**BUG-60 (MEDIUM) — `POST/PATCH /api/exercises` accepted non-http(s) `default_video_url`.** `javascript:alert(1)` was accepted and stored verbatim, unlike the equivalent doc-URL fields on agreements/bug-reports which already enforce an http/https allowlist. Fix: added the identical `new URL()` + protocol check to both the create and update handlers (`app/api/exercises/route.ts`, `app/api/exercises/[id]/route.ts`). Verified live: `javascript:` now 400s on both create and update; `https://` still 201s.

**BUG-63 (MEDIUM) — `GET /api/inactivity-response` crashed with a raw 500 on a malformed token.** `verifyToken()` in `lib/inactivity-token.ts` called `timingSafeEqual()` without checking both buffers were the same length first; any signature that didn't decode to exactly 32 bytes threw an uncaught `RangeError` instead of degrading gracefully — notable because this is a public, no-login endpoint hit by arbitrary email-link scanners/proxies. Fix: explicit length check before the constant-time comparison, returns `null` (→ friendly error page) instead of throwing. Unit-verified with a standalone script (5 cases: valid token, short/oversized/missing/empty signature — all pass) and live-verified against the running dev server (malformed token now returns 400, not 500).

**Not fixed — BUG-61 (MEDIUM, deferred).** SessionBuilder's direct-to-Supabase write path (`components/pt/SessionBuilder.tsx`) still has no server-side validation. The 2026-06-30 fix for the same bug number added `stripHtmlTags()` *inside* that client component, but that's not a real control — replaying the write via direct Supabase REST calls with the PT's own JWT (exactly how Phase 1b found it) bypasses it entirely and still accepts raw `<script>` tags, SQL-injection-shaped strings, and unbounded title length. Properly fixing this means adding a new `POST/PATCH /api/sessions` route matching the `exercises`/`templates` validation pattern and switching `SessionBuilder.tsx` over to it — a bigger, riskier change than tonight's budget/time justified. Logged as **Notion BUG-67** (open) for a future night.

**Not a bug — BUG-58.** Phase 1a's "6 duplicate Smoke Test Squat exercises" is leftover data from nights *before* the 2026-06-30 process fix (which stopped creating a new one every run), not a new defect — tonight's run correctly reused an existing one.
